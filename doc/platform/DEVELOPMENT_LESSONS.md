# 本次开发经验与后续约定

更新日期：2026-10-22。本文件记录改进开发方式的依据。它约束后续迁移，不把约定本身算作功能已完成；实际进度见 [工作记录](WORK_LOG.md)。

## 1. 同一种机器人能力只维护一条实现链

旧平台完整聊天链路经过 DSH，后来用户自带 Key 又增加了独立纯文本链路。结果不是简单换了费用来源，而是看图、搜索、工具、记忆等能力不再一致；从用户看来像管理员和普通用户在使用两种等级的机器人。

后续所有适用对象使用同一聊天引擎，由明确的策略决定范围和开关。增加一个模型或自费来源，不能再复制一套消息处理、上下文、工具和记忆流程。

统一并非所有用户都能操作任何资源。群 A 的模型可使用看图工具，不代表可以读取群 B 的图片；普通用户的聊天能力完整，也不意味着可以管理平台设置或执行本地命令。

验收须在相同模型与配置下，对平台角色、不同费用来源和群/私聊执行共同场景。没有技术原因的差异视为缺口；模型不支持或权限不足必须明确说明原因。

## 2. 分清账号权限、资源范围、模型能力和付费来源

| 维度 | 回答的问题 | 不得据此推导 |
| --- | --- | --- |
| 平台角色 | 谁能管理平台账号和默认项 | 管理员聊天天然拥有更多模型能力 |
| 资源授权 | 谁能管理哪个群/私聊，工具能操作什么 | 绑定 QQ、填写群号或先申请就有管理权 |
| 模型与能力 | 当前模型支持哪些模态，哪些工具已启用 | 模型名称相同就保证所有接口行为相同 |
| 付费来源 | 谁明确承担哪一笔调用费用 | 有 Key 就获得平台管理权，Key 失效就改花平台的钱 |

平台管理员和普通账号是人的权限，机器人是消息身份，两者不能称成“上级机器人”和“普通机器人”。Key 仅影响费用与相应供应商配置，不应隐藏完整聊天能力。

## 3. 先定义通用对象，再处理具体业务

最初需求只说群聊，后续很快扩展到私聊和管理员私聊。如果一开始以“某个群的特殊配置”实现，每个入口都要补相似逻辑，容易遗漏权限、计费或上下文隔离。

后续使用稳定的机器人身份和完整会话身份，群与私聊即使号码相同也不能合并。管理员私聊仍是私聊。人设选择、预算、用量、档案和工具范围使用共同对象；只有明确的产品差异进入策略层。

后台记忆整理等任务必须明确归属原聊天或受限的平台任务，不能因为不是群消息就跳过身份和费用检查。

## 4. 会话、人设和缓存分别设计

原系统按群隔离上下文，不应仅因人设相同就认定消息会混乱。人设覆盖、当前档案、历史档案与供应商缓存是不同对象。

切换人设时保留可恢复档案，A → B → A 应能继续应用层保存的 A 档案；同时撤销旧人设尚未完成的工具与排队发言。不能把某个后端 ID 当成所有数据的完整证明，也不能承诺它能让供应商缓存永久有效。

新引擎与 DSH 的会话组织不同。迁移前先说明哪些历史能继续用于新提示词、哪些只能只读查看，不把旧 ID 换个字段名就宣称已恢复。

## 5. 群是共享资源，不由先填写的人占有

机器人入群、网页账号取得群管理权、开启付费聊天是三个状态。先申请者不能只凭群号获得该群。

同一机器人和群只保留一条记录，可关联多个有依据的管理账号；重复申请应进入同一资源，并发创建由存储约束处理。真实群主/群管理员身份来自可信 QQ 事件与核验，浏览器里的号码和角色声明不是证据。

群预算属于该群，同群多个管理者不能各获得一份预算。出资人的 Key 和消费上限须由其明确授权；群管理权限不等于任意支配他人的钱。身份变化、退出群、撤销授权要能影响后续操作与已排队任务。

## 6. 费用统计、预算准入和真实扣款不是同一功能

显示日报只能解释已有记录，不能阻止下一笔支出。只在唤醒入口检查余额，也挡不住一次唤醒里的多轮工具、记忆整理、重试和备选模型调用。

费用能力应覆盖每一次真实付费尝试：先确定归属和价格、原子预留、发请求、结算或保留待核对状态。已结算加在途预留参与判断；80% 的降频/缩短输出与 100% 的拒绝新调用是可测试的程序策略，不能只写在提示词里期待模型遵守。

明确北京时间换日、请求跨日、重复完成、取消、重启、缺少 usage、价格未知等情况。供应商计价和缓存字段不同，不能把旧单价原样套到所有模型。金额应说明是平台估算；未知费用不能假定为零，尚未上报用量也不能证明未扣款。

## 7. 通用 Provider 与工具能力仍须有信任边界

个人桌面工具由本机操作者填写 API 地址、安装插件，与向公网普通账号开放这些操作不是同一信任边界。上游支持任意兼容接口，并不意味着网页用户的 Key 可发送到任意地址，或能通过安装扩展执行任意代码。

多供应商需要明确的适配器、能力声明、出站策略和价格来源。跨供应商重试、备选模型及账号池只能选择当前出资人明确允许的凭据，不得静默借用平台 Key。供应商与 Key 的切换不得绕过工具范围、群权限和费用策略。

“通用”指共用接口与正确分层，不是把校验删掉以兼容所有输入。能力不足或策略拒绝要可解释，不能悄悄换一条权限更宽的路径。

## 8. 容量与接入可行性应先于完整托管流程

支持注册和实例登记，不等于能在小型服务器上大量运行独立 QQ。首次启动、常驻、活跃和并发阶段的 CPU、内存、存储、网络开销需要分别测量；测试只启动一个实例，不能推出可无限增加用户实例。

先说明每个 QQ 必须保留哪些进程、哪些后端可以共用，再决定名额、资源上限和超额行为。网页关闭不会释放常驻客户端；用户账号数量与 QQ 客户端数量不能混为一谈。

第三方接入能运行不代表腾讯官方授权，不能向用户保证不会被限制。官方机器人 API 属于另一接入路线，功能、身份和授权需重新核实；更换聊天引擎也不会自动更换 QQ 接入机制。

## 9. 页面开关必须对应完整可用闭环

本次出现过“工具勾选项存在，但真正总开关没有页面入口，素材库也未准备”的情况。单有后端函数或可勾选复选框，不能让普通用户完成使用。

一项能力需要同时核对：实际配置来源、可见入口、依赖与素材、模型支持、权限、执行结果、失败提示、费用策略、保存后的生效行为。多个开关必要时说明作用，避免用户勾选后无反馈。

没有 Key、没有授权或还未绑定 QQ 时，应显示下一步的直接入口，不能留下空下拉框和禁用按钮让用户猜。名称说清“模型 API 配置”“每日额度”等实际含义，避免让用户理解内部实现词汇。

## 10. 状态提示必须有对应证据

扫码初始化期间曾把桌面提示窗显示到扫码图片区，并过早显示“可以扫码”。当时没有取得该时刻的 X11 窗口映射状态，因此不据截图断言具体窗口状态或根因。能从桌面取得一张图片，不代表该图片就是用户可以使用的二维码。

页面应区分环境准备、QQ 启动、二维码可用、等待手机确认、身份核验、聊天服务就绪和已启用。每个状态说明由哪条真实检查支持；不能把创建目录、收到申请、生成图片或某个进程存在当成接入完成。

类似地，Key 已保存不代表供应商余额和权限有效；请求成功不代表消息已实际发出；主机本地响应成功不代表公网用户已能访问。

## 11. 测试数量不能代替真实用户闭环

很多隔离用例通过，仍可能遗漏实际页面里无法完成的一步。测试应验证用户从注册、身份验证、配置费用、人设切换到实际发言和限额的完整路径，并核对明确的副作用，而不是重复实现代码的分支。

共同验收矩阵至少包括以下维度；按实际能力选择组合，并为不适用项写出原因：

| 维度 | 需要覆盖的差异 |
| --- | --- |
| 操作者与费用 | 平台管理员/普通账号，平台出资/用户自费，Key 失效/被删除 |
| 聊天范围 | 群、私聊、管理员私聊、后台任务，不同机器人和同号不同类型对象 |
| 能力 | 文字、图片、搜索、工具追加轮次、记忆、已开启的语音或其他媒体 |
| 时间与并发 | 同群多人编辑、请求在途改人设/Key/授权、重复结算、跨日、重启 |
| 页面与设备 | 缺少准备项、错误恢复、草稿保留、导航、手机触控与溢出 |

同时区分纯模块测试、实际引擎加模拟 HTTP 的集成测试、真实浏览器、服务器运行与本人 QQ 操作。隔离模拟不证明真实 QQ 成功，视口模拟不证明实体手机键盘体验；旧版本的通过记录也不是新引擎的通过记录。未执行项和已知失败必须保留。

## 12. 小步迁移与可接手记录优先

先在独立仓库和分支建立 QQ Agent 基线、上游关系与测试证据，再迁移一项通用能力。先在隔离数据上验证导入和回退；不为测试方便重置生产账号、复制运行秘密、清空账本或重建会话。

每次提交说明问题、最终行为、验证结果、部署状态与剩余限制。明确区分代码已写、模块已测、已接入引擎、已部署和真实运行已验收。设计变化保留原因，不能把早期错误从历史中抹掉。

开发资料、上游署名与必要交接进入公共 Git；服务器连接、密钥、数据库、真实聊天和运行截图留在私有范围。多 Agent 并行须分配文件边界，合并后由同一套能力契约和测试确认，不让不同 Agent 再实现出几套不一致的能力。

## 每项新能力的交付检查

开始开发前，说明它操作哪个通用对象、复用哪条引擎路径、需要哪些权限和费用归属。完成时同时提供实际调用接线、用户入口、依赖/失败提示和适用矩阵验证；尚未完成的部分明确标记，不能用一个界面开关代替完整交付。
